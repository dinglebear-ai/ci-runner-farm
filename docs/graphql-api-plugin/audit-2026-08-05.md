# Accuracy audit: Runner Farm Unraid GraphQL plugin design

Date: 2026-08-05

## Scope

This audit re-reviewed every file in `docs/graphql-api-plugin` against:

- CI Runner Farm at `086274a45ec4f598e8013f9d109cd2983cfce4e4`;
- Unraid API `origin/main` at `98034ff8405d8f1322daca9bd4d7d7dccc262810` (API 4.36.1);
- the current Rust Unraid MCP layout under `/home/jmagar/workspace/unraid-mcp/unraid-rs`;
- local npm fixtures for tarball install/no-op behavior and removal after a root dependency entry is lost.

The review covered the public SDL, all TypeScript references, normative contracts, research/specification documents, upstream proposal, packaging lifecycle, MCP surface, and every implementation-plan task.

## Corrections made

### 1. Updated the Runner Farm baseline

The design worktree was fast-forwarded twice as `origin/main` advanced during the audit. The final reviewed Runner Farm commit is `086274a`, including the exhaustive pool lifecycle/readiness hardening merged in pull request 20.

### 2. Corrected Unraid API reboot discovery

The original design assumed the dependency archive made runtime peer-dependency edits reboot-durable. The reviewed archive stores only `node_modules`; current discovery also depends on the API root `package.json`, which is not archived.

The upstream design now requires configured canonical-name discovery directly from exact top-level package manifests. Configuration remains the allowlist; no arbitrary package scan is introduced.

### 3. Separated same-version reboot from API-version upgrade

A version-specific dependency archive can restore a package after a same-version reboot. It is not the source of truth for a newly installed API version.

Runner Farm now retains its tarball on flash and has an idempotent, bounded reconciler that can reattach the module after an API-version upgrade and tolerate either Unraid-plugin boot order.

### 4. Corrected archive transaction ordering

The official CLI already invokes archive rebuild. The Runner Farm installer must not duplicate that work.

For the interim path, installation and atomic archive replacement happen before canonical enablement. Archive failure preserves the previous archive and leaves enablement unchanged.

### 5. Added cross-process plugin transaction coordination

Current CLI, GraphQL, and third-party reconcilers can race npm, archive, config persistence, and restart. The corrected upstream design adds one bounded cross-process owner-verified transaction lock. GraphQL mutations explicitly await durable config persistence and hand lock ownership to restart so the 300 ms delay cannot admit a second mutation.

### 6. Corrected plugin verification claims

Current `plugins list` reports name and version, not `hasApiModule`. The plan now proposes an upstream `plugins verify <canonical-name>` command or an exact supported equivalent. Authenticated GraphQL smoke verification is optional and requires an explicitly supplied test/admin API key.

### 7. Added fresh root-manifest reads

Unraid API's `getPackageJson()` loads through Node `require` and is cached. Before/after npm comparisons now explicitly use fresh bounded file reads from `getPackageJsonPath()`.

### 8. Corrected removal after reboot

A DOOKIE fixture confirmed `npm uninstall <canonical-name>` removes a restored top-level package even after the root dependency entry is removed. The plan preserves that behavior with a regression test instead of adding an unnecessary direct-delete fallback.

### 9. Removed lossy status modeling

The existing UI-oriented schema-v2 status rounds CPU limits to whole cores, memory limits to whole GiB, uses negative unknown-usage sentinels, shortens image IDs, reports image size in integer MiB, and emits several IDs as JSON numbers.

The strict API and GraphQL schema now add nullable exact CPU millicores and byte limits, nullable usage, full image identity and exact bytes, and string forms of potentially unsafe numeric identifiers.

### 10. Preserved invalid read state and readiness uncertainty

Backend, mode, or auth configuration can be invalid. Read-side state enums now include `INVALID`; valid configuration inputs remain narrower selection enums. Readiness now carries a nullable cached fleet count: mode-0600 regular inventory produces an integer, while missing, symlinked, oversized, or unsafe-mode inventory remains unknown without refreshing Docker.

### 11. Preserved all configuration sentinels

The controller has 48 allowlisted keys. The corrected configuration model round-trips:

- empty uncapped CPU/memory values;
- resource budgets set to `auto`;
- workspace tmpfs versus cache bind;
- pool autoscale `inherit` versus an explicit empty/non-empty set;
- nullable strings used to clear auth/image/registry fields;
- memory swap `none` or `double` only.

The configuration query now returns revision, validity/issues, nullable typed configuration, canonical effective strings for all 48 keys, one opaque credential revision, and credential-presence booleans. It remains useful when the current file is invalid.

### 12. Corrected invented limits

The original references invented repository/additional-label count caps, autoscale interval/grace bounds, a PIDs upper bound, an `unlimited` swap value, a seven-day image-update maximum, and a 255-byte registry-token limit.

Those were replaced with actual controller semantics. The registry token limit is 4096 bytes; image update is 300-86400 seconds; drain timeout is 0 or 60-86400 seconds; pool count is eight and serialized pool configuration is 16 KiB.

### 13. Added an independent credential revision

Secret files are not part of `configRevision`, so config revision alone could not detect concurrent secret changes. The configuration snapshot now exposes a random opaque credential revision backed by a private fingerprint state file. Secret set/clear requires both revisions and reconciles legacy/crash mismatch before comparison without exposing secret hashes.

### 14. Strengthened other revision requirements

Fleet lifecycle, scale, and recycle now require both configuration and inventory revisions. Partial configuration validation/apply, secret set/clear, prewarm, maintenance, cache clear, provisioning validation, and compatibility start require the current configuration revision. Migration retains all four authorities.

Dockerfile save now requires the SHA-256 of the content previously read; image build requires the SHA returned by save.

### 15. Added explicit resource availability and hardened state projection

The latest controller resets resource quantities to zero when the live resource snapshot is unavailable and rejects unsafe-mode/symlinked snapshots, reservations, ownership, plans, compatibility records, and operation files. The strict GraphQL resource model now adds `available` and a stable reason so fail-closed zero values cannot be mistaken for real capacity. Reservation projection preserves only the current phase set and bounded positive CPU, memory, and deadline values.

### 16. Added a durable generic operation journal

Current compatibility and image-build operation state is tmpfs/runtime-local and provisioning validation is synchronous.

The design now requires a low-frequency mode-0600 metadata journal under `$CFGDIR/operations`, exact UUID lookup, bounded retention/output references, high-volume logs off flash, and boot reconciliation that marks abandoned non-terminal work `operation_interrupted`.

### 17. Corrected lock ownership

The reviewed `cmd_start`, `cmd_stop`, and `cmd_restart` functions are already unlocked; dispatch owns `with_fleet_lock`. The plan no longer proposes redundant `*_unlocked` functions and instead adds tests that preserve single lock ownership.

### 18. Corrected code-first GraphQL names

Reference classes use a `Model` suffix. Plain `@ObjectType()` would have generated public types ending in `Model`, contradicting the SDL. Every output model now explicitly binds its public SDL name.

### 19. Corrected SDL/model type and nullability drift

The SDL and reference classes were aligned for exact fields, configuration snapshots, specific secret inputs, fleet versus config revision inputs, defaulted non-null log line count, and required operation `createdAt`.

### 20. Corrected package dependency ownership and metadata

Framework singleton packages are compatible peers. Execa and Zod are plugin-owned dependencies. Runner Farm remains Apache-2.0. `unraidVersion` metadata is generated and verified from the current official generator and host matrix instead of being omitted or blindly frozen.

### 21. Corrected queue and MCP bounds

The controller's detailed queue snapshot is capped at 40 rows, not 50. MCP projections and fixtures now preserve exact millicores, byte quantities, invalid configuration state, unsafe-size ID strings, and interrupted durable operations.

### 22. Increased implementation-plan granularity

Large model/schema/controller/packaging tasks were split into focused tasks with unique IDs. The plan now has separate work for state enums, output groups, configuration inputs, legacy/raw schemas, exact augmentation, operation durability, mapping sentinels, direct discovery, archive atomicity, same-version reboot, API upgrade, and MCP projections.

## Remaining implementation-time gates

These are not documentation defects and cannot be proven by static review alone:

- the upstream release/version that first contains all three installation capabilities;
- the final supported Unraid host/version matrix for `unraidVersion`;
- the exact upstream CLI name if maintainers choose a verification command other than `plugins verify`;
- live API-key permission checks;
- same-version offline reboot on an approved Unraid host;
- API-version upgrade reconciliation with uncertain plugin boot order;
- live MCP calls through Labby after deployment.

- 262 unique implementation task IDs with no duplicates.
- GraphQL semantic construction: 91 definitions, 85 Runner Farm types, 12 queries, 23 mutations, and 2 subscriptions.

- SDL and code-first references have exact field-name, GraphQL type, default-value, and nullability parity.
- All eight TypeScript reference files compile under TypeScript 5.9.2 against the reviewed Unraid API dependency graph.
- 57 internal documentation references were checked with none missing.
- No trailing whitespace, NUL bytes, CR characters, or unbalanced Markdown fences were found.
- Runner Farm source evidence reconfirmed 48 allowlisted configuration keys, 64-runner and eight-pool limits, the 16 KiB serialized-pool limit, the 4096-byte registry-token limit, and current image-update/drain bounds.
- Unraid API source evidence reconfirmed that the dependency archive contains only node_modules, discovery currently filters through the root manifest, the current installer mutates config before npm, the official installer rebuilds the archive internally, and GraphQL plugin mutations schedule a delayed restart without an explicit awaited persist.
- A fresh npm fixture reconfirmed canonical tarball install metadata, empty add/change arrays for a no-op reinstall, canonical peer saving through a file spec, and successful uninstall after the root dependency entry is removed.

## Repository effects

This audit changed only the documentation/design package and its implementation-shaped reference files. No Runner Farm runtime implementation, Unraid API source, or Unraid MCP source was modified during the audit.
